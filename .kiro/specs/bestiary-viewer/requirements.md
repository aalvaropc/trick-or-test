# Requirements Document

## Introduction

The bestiary viewer is the static web application in `apps/viewer`. It opens a Trick or Test run, or any plain StrykerJS JSON report, entirely in the browser, and shows which mutants survived the tests and which acceptance criteria are unguarded. Every mutant is drawn as a creature: species encodes the mutation type and state encodes the test outcome. The visual system (palette, type, species, states, seals, motion, voice) is defined in `.kiro/steering/bestiary.md` and is binding. The stack is defined in `.kiro/steering/tech.md`.

The viewer reads report shapes from the engine subpath `trick-or-test/report` only (ADR 0002, `structure.md`). It has no backend, makes no network request with user data, and is hosted on GitHub Pages under `/trick-or-test/`.

The static design reference in `.trickortest/design/project/` (`Main.dc.html`, `Verdict.dc.html`, `Specimen.dc.html`) defines the page layout of each screen. Requirement 13 takes its palette, page width, header, grid and sizes into the style sheets of the Viewer. Its font CDN link, its gradients, its glows, its turbulence filter and its text sizes below 14 CSS pixels are not part of this spec, and no number of the reference enters the Creature_Generator.

The README and the demo video link straight to the demo routes `#/demo/before` and `#/demo/after`. Requirement 14 defines how the demo runs are generated and which files the Viewer reads from them.

Out of scope: the format of the lock log (owned by the agent-guard spec), the engine's `measure` command itself, and sound. The root script that calls `measure` to produce the demo runs is in scope (Requirement 14).

## Glossary

- **Viewer**: The static single-page application in `apps/viewer`.
- **Run**: One Trick or Test measurement, made of a Mutation_Report and optionally a Verdict_File and a History_File.
- **Mutation_Report**: A JSON file that conforms to `mutation-testing-report-schema`, as parsed by `mutationReportSchema`.
- **Plain_Stryker_Report**: A Mutation_Report produced by StrykerJS alone, without the Trick or Test extension fields (`species`, `requirement`) and without a Verdict_File.
- **Verdict_File**: The optional sidecar `verdict.json`, as parsed by `verdictSchema`.
- **History_File**: The optional append-only JSON Lines file (`history.jsonl` as the engine writes it) with one JSON history record per non-empty line and one line appended per run, each parsed by `historyRecordSchema`.
- **Lock_Log**: The optional log of blocked write attempts, whose format the agent-guard spec defines.
- **Loader**: The Viewer component that reads, parses and validates user-supplied files and bundled demo files into a Run.
- **Run_Model**: The in-memory, validated representation of a Run that every screen reads.
- **Mutant**: One entry of the Mutation_Report, joined by id with its Verdict_File entry when present.
- **Spec_Mutant**: A Mutant tied to an acceptance criterion; it has a `requirement` id.
- **Stray**: A Mutant without a `requirement` id (a mechanical mutant).
- **Criterion**: One acceptance criterion with an id `<requirement>.<criterion>`.
- **Coverage_Status**: One of guarded, unguarded, unattacked or skipped.
- **Kill_Class**: One of examples-only, properties-only, both or unattributed.
- **Creature_Generator**: The pure function `creature(species, seed, state)` that returns an SVG string.
- **Species**: One of Borderling, Miscount, Two-Face, Hollow, Impostor, Oathbreaker or Unclassified.
- **Creature_State**: One of survivor, killed, in the dark or ghost, as defined in `bestiary.md`.
- **Seal**: The drawing of a Criterion's Coverage_Status: closed, cracked, empty, or the skipped mark.
- **Landing_Screen**: The first screen, with the pitch, the demo links and the drop zone.
- **Verdict_Screen**: The screen with the headline, the seals, the who-killed-them panel, the strays strip and the species legend.
- **Specimen_Screen**: The screen that shows one Mutant in detail.
- **Hunt_Screen**: The screen that shows the timeline of runs from the History_File.
- **Plain_View**: The sortable table of the same data, with no creatures and no animation.
- **Demo_Run**: A bundled Run in `apps/viewer/public/demo/`, generated by the engine's measure command.
- **Fixture_Run**: A small Run under `apps/viewer/test/fixtures/` used by tests until the Demo_Runs exist.
- **Narrow_Screen**: A viewport 360 CSS pixels wide or wider and narrower than 768 CSS pixels.
- **Page_Frame**: The shared layout of every screen: the centred content column with its maximum width and side padding, and the header with the product mark, the screen title, the navigation and a bottom rule.
- **Screen_Title**: The text of the single `<h1>` of a screen, written in the product's words, as opposed to the internal screen name.
- **Creature_Size**: The width and height in CSS pixels that the Viewer gives to the creature SVG in one place of the interface (seal grid, who-killed-them panel, strays strip, species legend, Hunt_Screen, Specimen_Screen).
- **Surface_Token**: A CSS custom property for a surface or rule colour that Requirement 13 adds to the six colour tokens of `bestiary.md`.
- **Demo_Generator**: The script at the repository root, run with `npm run demo`, that generates both Demo_Runs with the engine's `measure` command.
- **Guard_Test**: The one extra committed test file, outside `examples/pricing/test/`, that guards criterion 7.4 of the `cart-pricing` spec in the "after" Demo_Run.

## Requirements

### Requirement 1: Open a run from local files

**User Story:** As a developer, I want to open my report files in the browser, so that I can inspect a run without uploading anything.

#### Acceptance Criteria

1. WHEN the user drops files on the drop zone or selects files with the file picker, THE Loader SHALL read the files with browser APIs and send no file content over the network.
2. WHEN a supplied file is a valid Mutation_Report, THE Loader SHALL build a Run_Model from the Mutation_Report and display the Run_Model.
3. WHERE a valid Verdict_File is supplied with a Mutation_Report, THE Loader SHALL join each Verdict_File mutant to the Mutation_Report Mutant that has the same mutant id.
4. WHERE a valid History_File is supplied, THE Loader SHALL parse each non-empty line as one history record with `historyRecordSchema` and order the records by their `time` field, oldest first, keeping the original file order for records with equal `time` values.
5. WHEN a Plain_Stryker_Report is supplied, THE Loader SHALL build a Run_Model in which each Mutant has the species derived from its mutator name and has no Criterion data.
6. THE Loader SHALL recognise each supplied file as Mutation_Report, Verdict_File, History_File or Plain_Stryker_Report from its content, not from its file name, and WHEN the whole content of a file is one JSON document with the shape of a Mutation_Report or a Verdict_File, THE Loader SHALL recognise it as that kind and SHALL NOT test it as a History_File.
7. IF a supplied file is neither valid JSON nor a History_File under criterion 12, THEN THE Loader SHALL show an error that names the file and describes the parse failure, and SHALL keep any previously loaded Run_Model unchanged.
8. IF a supplied file other than a History_File fails its zod schema, THEN THE Loader SHALL show an error that names the file and the path of each failing field (up to 10 paths, followed by the count of any further failures), and SHALL keep any previously loaded Run_Model unchanged.
9. IF the supplied files contain no Mutation_Report and no Plain_Stryker_Report, THEN THE Loader SHALL show an error that states a Mutation_Report is required, and SHALL keep any previously loaded Run_Model unchanged.
10. IF a Verdict_File lists a mutant id that the Mutation_Report does not contain, THEN THE Loader SHALL ignore that entry and show a note with the count of ignored entries.
11. IF a file selected by the user exceeds 50 MB (52,428,800 bytes), THEN THE Loader SHALL reject the file without reading its content and show an error that names the file and the 50 MB limit.
12. WHEN a supplied file is not a Mutation_Report or a Verdict_File under criterion 6 AND at least one of its non-empty lines parses as JSON and validates with `historyRecordSchema`, THE Loader SHALL recognise the file as a History_File, SHALL ignore blank lines (empty or whitespace-only lines), and SHALL accept a trailing newline with either the LF or the CRLF line ending.
13. IF a History_File has a non-empty line that is not valid JSON or fails `historyRecordSchema`, THEN THE Loader SHALL reject the whole file, show an error that names the file, the 1-based line number of the first such line counted over all lines including blank ones, and the parse failure or the path of each failing field of that line (up to 10 paths, followed by the count of any further failures), and keep any previously loaded Run_Model unchanged.
14. IF a supplied file has zero non-empty lines (zero bytes or only whitespace), THEN THE Loader SHALL NOT recognise it as a History_File, SHALL show an error that names the file and states that it is empty, and SHALL keep any previously loaded Run_Model unchanged.

### Requirement 2: Open the bundled demo runs

**User Story:** As a visitor, I want to open a demo run in one click, so that I can see the viewer working without having my own report.

#### Acceptance Criteria

1. THE Landing_Screen SHALL show exactly two demo links: one link to the Demo_Run recorded before the hunt and one link to the Demo_Run recorded after the hunt, each with a visible text label that identifies which run it opens.
2. WHEN the user activates a demo link, THE Loader SHALL fetch every file of the selected Demo_Run from the same origin under `/trick-or-test/demo/`, and THE Viewer SHALL open the Verdict_Screen for that Demo_Run.
3. IF a Demo_Run file cannot be fetched because of a network failure, a not-found response, or no response within 10 seconds, THEN THE Loader SHALL show an error that names the file that failed, SHALL keep the Landing_Screen open, SHALL NOT open the Verdict_Screen, and SHALL leave both demo links active so the user can retry.
4. IF a Demo_Run file is fetched but cannot be parsed as a valid report, THEN THE Loader SHALL show an error that names the file and states that its content is invalid, SHALL keep the Landing_Screen open, and SHALL NOT open the Verdict_Screen.
5. THE Viewer SHALL read the Demo_Run files without modifying them, and SHALL send only read requests (no requests that write or delete) for them.
6. WHILE the Demo_Runs do not exist in `apps/viewer/public/demo/`, THE Viewer test suite SHALL use the Fixture_Runs under `apps/viewer/test/fixtures/` in place of the Demo_Runs.
7. WHEN the page is opened with the hash route `#/demo/before` or `#/demo/after`, THE Viewer SHALL load the Demo_Run recorded before the hunt or after the hunt respectively, and show its Verdict_Screen.
8. WHEN the user reloads the page on the route `#/demo/before` or `#/demo/after`, THE Viewer SHALL load that Demo_Run again and show its Verdict_Screen.
9. IF loading the Demo_Run of a demo route fails as described in criterion 3 or criterion 4, THEN THE Viewer SHALL show the Landing_Screen with the error defined in that criterion and SHALL leave both demo links active.

### Requirement 3: Landing screen

**User Story:** As a visitor, I want a short pitch backed by real numbers, so that I understand what the tool shows before I open a run.

#### Acceptance Criteria

1. WHEN the Landing_Screen is displayed AND the Demo_Run recorded before the hunt has loaded successfully, THE Landing_Screen SHALL show a pitch sentence containing exactly two numbers: the count of surviving mutants and the count of unguarded Criteria, both computed from that Demo_Run.
2. IF the Demo_Run recorded before the hunt fails to load, is not valid as a Run, or has not finished loading within 5 seconds, THEN THE Landing_Screen SHALL show the pitch sentence without any numbers, SHALL keep the drop zone usable, and SHALL NOT show a count of 0 in place of the missing numbers.
3. THE Landing_Screen SHALL show the statement that files never leave the browser, visible without scrolling or any user interaction.
4. THE Landing_Screen SHALL show the drop zone.
5. WHEN a user focuses the file picker control of the drop zone using the Tab key and presses Enter or Space, THE Landing_Screen SHALL open the file picker so that a Run file can be chosen without using a pointer.
6. THE Landing_Screen SHALL derive each number in the pitch sentence from a loaded Run, and its source SHALL contain no hard-coded count.

### Requirement 4: Derive mutant state and species

**User Story:** As a developer, I want each mutant mapped to one species and one state, so that the drawing encodes the same facts as the data.

#### Acceptance Criteria

1. THE Viewer SHALL map each mutator name to exactly one Species using a single mapping table in code that contains the same mutator-name-to-Species entries as the table in `.kiro/steering/bestiary.md`.
2. THE Viewer SHALL map each Spec_Mutant to the Oathbreaker species, regardless of its mutator name.
3. IF a mutator name is not in the mapping table, THEN THE Viewer SHALL map the Mutant to the Unclassified species, keep rendering all other Mutants, and not throw an error.
4. WHEN a Mutant has the report status `Survived`, THE Viewer SHALL assign the survivor state.
5. WHEN a Mutant has the report status `Killed` or `Timeout`, THE Viewer SHALL assign the killed state.
6. WHEN a Mutant has the report status `NoCoverage`, THE Viewer SHALL assign the in-the-dark state.
7. WHEN a Mutant has the Trick or Test status `Ghost` (taken from the Verdict_File, or derived under criterion 12), THE Viewer SHALL assign the ghost state.
8. WHEN a Mutant has a status other than `Survived`, `Killed`, `Timeout`, `NoCoverage` or `Ghost` (including a status `Ignored` that criterion 12 does not map to the ghost state), THE Viewer SHALL draw no creature for the Mutant, exclude it from every count, and list it in the Plain_View under the label "not counted".
9. WHERE a Verdict_File is present, THE Viewer SHALL take the Mutant status and species from the Verdict_File entry whose id equals the Mutant id.
10. IF a Verdict_File is present and has no entry for a Mutant id, THEN THE Viewer SHALL use the status and species derived from the report for that Mutant and not throw an error.
11. THE Viewer SHALL compute every count it shows from the Run_Model, so that the headline, the legend, the Plain_View and the Hunt_Screen show identical numbers for the same Run.
12. WHERE no Verdict_File is present, THE Viewer SHALL read the `statusReason` of each Mutant with the report status `Ignored`, so that a Mutant whose `statusReason` names `Ghost` gets the ghost state, and a Mutant whose `statusReason` names `InvalidWitness`, names `NotApplicable`, names any other engine status, or is missing is listed in the Plain_View under the label "not counted" with no creature.

### Requirement 5: Creature generator

**User Story:** As a developer, I want creatures produced by a pure function, so that the same mutant always looks the same and can be tested.

#### Acceptance Criteria

1. WHEN the Creature_Generator is called with a species, a seed and a Creature_State, THE Creature_Generator SHALL return a single SVG string for that combination.
2. WHEN the Creature_Generator is called twice with identical species, seed, Creature_State and mutant arguments, THE Creature_Generator SHALL return byte-identical strings.
3. THE Creature_Generator SHALL derive all variation from a seeded pseudo-random generator initialised only from the seed, and SHALL read neither the system clock nor any unseeded random source.
4. THE Creature_Generator SHALL produce a body of 3 to 5 cubic curves per creature, with seeded jitter of each control point no greater than 8% of the `viewBox` width, inside a `viewBox` that is the same for every species, seed and state.
5. THE Creature_Generator SHALL keep the number of body curves and the sequence of element kinds of each species identical for every seed, so that jitter changes proportions only.
6. THE Creature_Generator SHALL give the root `<svg>` element the attribute `role="img"` and a `<title>` child whose text is "<Species>, <state>: <file>:<line>", where `<file>` and `<line>` are the file path and line number of the mutant, or is "<Species>, <state>: unknown location" when criterion 15 applies.
7. WHEN the state is survivor, THE Creature_Generator SHALL draw the body with full-ink stroke and fill and SHALL draw eyes using the lit-eye colour token from `bestiary.md`.
8. WHEN the state is killed, THE Creature_Generator SHALL draw bones only, using a stroke width no greater than half the survivor stroke width, with no body fill and no eyes.
9. WHEN the state is in the dark, THE Creature_Generator SHALL draw the body as a filled silhouette in a single colour token and SHALL draw no eye elements.
10. WHEN the state is ghost, THE Creature_Generator SHALL draw the body as a dashed outline with no fill at an opacity of exactly 0.4.
11. THE Creature_Generator SHALL draw inside the body bounds the glyph of the exact code change (the original and replacement text of the mutant), using the glyph rule of the species defined in `bestiary.md`.
12. THE Creature_Generator SHALL use only colour tokens defined in `bestiary.md` for every fill and stroke value, and SHALL emit no `linearGradient`, `radialGradient`, `filter` or drop-shadow element.
13. WHERE the creature includes shade, THE Creature_Generator SHALL render the shade as an SVG `<pattern>` element made of parallel lines at a single angle.
14. THE Creature_Generator SHALL escape the characters `&`, `<`, `>`, `"` and `'` in every text value it places in the SVG, so that a file path or glyph containing those characters yields well-formed XML.
15. THE Creature_Generator SHALL NOT throw for any input. WHEN the file, the line or the glyph text of a mutant is missing or empty (for example in a Plain_Stryker_Report or a mutant without a location), THE Creature_Generator SHALL use "?" as the glyph and "unknown location" in the `<title>` in place of the missing value, and SHALL still return a valid SVG string.
16. FOR ALL species, seeds and states, including inputs with a missing or empty file, line or glyph, THE Creature_Generator SHALL return output that parses as well-formed XML with exactly one root `<svg>` element and SHALL NOT throw (invariant property).
17. FOR ALL species and states, two different seeds SHALL produce SVG with the same count of body curves and the same sequence of element kinds (topology invariant property).
18. FOR ALL species, seeds and states, calling the Creature_Generator twice with the same arguments SHALL return equal strings (determinism property).

### Requirement 6: Verdict screen

**User Story:** As a developer, I want one screen that tells me which criteria are guarded and which are not, so that I see the weak spots of my tests at once.

#### Acceptance Criteria

1. WHEN a Run with a Verdict_File is open, THE Verdict_Screen SHALL show a headline containing four counts taken from the Run_Model: surviving Spec_Mutants, killed Spec_Mutants, guarded Criteria and unguarded Criteria, each as a non-negative integer.
2. WHEN a Run with a Verdict_File is open, THE Verdict_Screen SHALL show exactly one Seal per Criterion in the Verdict_File coverage list, labelled with the Criterion id.
3. WHEN a Criterion has the status guarded, THE Verdict_Screen SHALL draw a closed Seal labelled "guarded".
4. WHEN a Criterion has the status unguarded, THE Verdict_Screen SHALL draw a cracked Seal labelled "unguarded" with each surviving Spec_Mutant of the Criterion drawn on the Seal.
5. WHEN a Criterion has the status unattacked, THE Verdict_Screen SHALL draw an empty Seal labelled "no mutant bred".
6. WHEN a Criterion has the status skipped, THE Verdict_Screen SHALL draw a skipped mark and show the skip reason from the Verdict_File.
7. IF a Criterion has a status other than guarded, unguarded, unattacked or skipped, THEN THE Verdict_Screen SHALL draw a Seal labelled with the Criterion id, show an indication that the status is unrecognised, and continue to render the remaining Seals.
8. WHEN a Run with a Verdict_File is open, THE Verdict_Screen SHALL show a "who killed them" panel with four groups: examples only, properties only, both, and unattributed, each with the count of killed Mutants of that Kill_Class, including a count of 0 for an empty group.
9. WHEN the user opens a group in the "who killed them" panel, THE Verdict_Screen SHALL list every Mutant of that group, and WHEN the group is empty, THE Verdict_Screen SHALL show an indication that the group has no Mutants.
10. WHEN a Run is open, THE Verdict_Screen SHALL show a strip of Strays with one creature per Stray, up to 60 creatures.
11. WHERE the Run has more than 60 Strays, THE Verdict_Screen SHALL draw the first 60 in the strip ordered by status, then file, then line, and show the count of the remaining Strays with a link to the Plain_View.
12. WHEN a Run is open, THE Verdict_Screen SHALL show a species legend with the name, body description, mutation type and count of Mutants for each Species present in the Run, and omit Species with 0 Mutants.
13. WHEN the user activates a creature by click, tap, or the Enter or Space key while it has keyboard focus, THE Viewer SHALL open the Specimen_Screen for that Mutant.
14. WHEN a Run has no Verdict_File, THE Verdict_Screen SHALL show the headline from the Mutation_Report counts alone, omit the Seals and the who-killed-them panel, and show a message stating that no verdict file was loaded.
15. THE sum of the counts in the four Kill_Class groups SHALL equal the count of Killed Mutants that have a Kill_Class (invariant property).
16. FOR ALL Verdict_Files, the number of Seals drawn SHALL equal the number of entries in the coverage list (invariant property).

### Requirement 7: Specimen screen

**User Story:** As a developer, I want to inspect one surviving mutant, so that I know what change my tests missed and which criterion it breaks.

#### Acceptance Criteria

1. WHEN the user opens a Mutant, THE Specimen_Screen SHALL show the creature at large size, its Species name, its state label and the mutant id.
2. WHEN the user opens a Mutant, THE Specimen_Screen SHALL show the code change as two lines, the original line and the mutated line, together with the file path and the 1-based line number.
3. WHERE the Mutant is a Spec_Mutant, THE Specimen_Screen SHALL show the id and the full text of the Criterion that the Mutant breaks.
4. WHERE the Verdict_File holds a witness for the Mutant, THE Specimen_Screen SHALL show the witness input, the expected value and the value of the Mutant.
5. WHEN the user opens a killed Mutant, THE Specimen_Screen SHALL list the names of the tests that killed the Mutant, up to 50 tests, and SHALL show the Kill_Class.
6. WHEN the user opens a surviving Mutant that has at least one entry in `coveredBy`, THE Specimen_Screen SHALL list the names of the tests from `coveredBy` that ran the mutated code without failing, up to 50 tests.
7. WHEN the user opens a Mutant that is in the dark, THE Specimen_Screen SHALL show the text "no test runs this code".
8. WHILE the Specimen_Screen is open and the user has not requested reduced motion, THE Specimen_Screen SHALL turn the creature's eyes toward the pointer position and update them on each pointer movement.
9. WHERE the user prefers reduced motion, THE Specimen_Screen SHALL keep the creature's eyes fixed in their default position and SHALL NOT animate them.
10. IF the requested mutant id is not in the Run_Model, THEN THE Specimen_Screen SHALL show a message that contains the requested id and a link to the Verdict_Screen, and SHALL NOT show any creature or code change.
11. IF the Mutation_Report holds no source text for the Mutant, THEN THE Specimen_Screen SHALL show the mutant's `replacement` and its file path and line number, and SHALL show a statement that the original line is unavailable.
12. WHEN the user opens a Mutant whose Criterion is absent from the Verdict_File, THE Specimen_Screen SHALL omit the Criterion section and SHALL show the remaining sections.

### Requirement 8: Hunt screen

**User Story:** As a developer, I want a timeline of my runs, so that I see how the tests killed creatures over time.

#### Acceptance Criteria

1. WHEN a History_File is loaded, THE Hunt_Screen SHALL show one timeline entry per history record, ordered by run time ascending (oldest first), and records with identical run times SHALL keep their order from the History_File.
2. THE Hunt_Screen SHALL show for each entry the run time, the git commit, the creatures in `newlyKilledIds`, and the number of surviving Mutants after that run.
3. THE Hunt_Screen SHALL compute the number of survivors after each run as the `Survived` value of the `statusCounts` of the history record.
4. WHEN the user activates a creature in a timeline entry, THE Viewer SHALL open the Specimen_Screen for that Mutant.
5. IF a mutant id in `newlyKilledIds` is absent from the current Run_Model, THEN THE Hunt_Screen SHALL show the id as text without a creature, and the id SHALL NOT be activatable.
6. WHERE a Lock_Log is loaded, THE Hunt_Screen SHALL show each blocked write attempt on the timeline in `--amber`, with the text label "blocked".
7. WHILE no Lock_Log is loaded, THE Hunt_Screen SHALL show the timeline without blocked attempts and without an error.
8. IF no History_File is loaded, THEN THE Hunt_Screen SHALL show a message stating that no history was loaded, and SHALL show no timeline entries. The Loader gives such a Run_Model an empty history list.
9. THE Hunt_Screen SHALL present the timeline as a static ordered list, and SHALL show all entries and their content with animation disabled.
10. IF the Run_Model holds a history list with zero records (the Loader builds none from a file, by Requirement 1 criterion 14), THEN THE Hunt_Screen SHALL show the same message as in criterion 8, stating that no history was loaded, and SHALL show no timeline entries. A Run_Model cannot tell an absent History_File from an empty list, and a loaded History_File always holds at least one record.
11. FOR ALL History_Files, the number of timeline entries SHALL equal the number of records (invariant property).
12. FOR ALL history records, the survivor count shown SHALL equal `statusCounts.Survived` of the record (invariant property).

### Requirement 9: Plain view

**User Story:** As a developer who prefers text, I want the same data as one sortable table, so that I can scan and sort without creatures or animation.

#### Acceptance Criteria

1. THE Viewer SHALL provide a link or control to the Plain_View on every screen.
2. THE Plain_View SHALL show exactly one table row per Mutant in the Run, with the columns mutant id, species, state label, status, Criterion id, file and line, and Kill_Class.
3. WHEN the user activates a column header, THE Plain_View SHALL sort all rows ascending by that column and indicate the sort direction in visible text ("ascending" or "descending").
4. WHEN the user activates the column header of the column that is currently sorted, THE Plain_View SHALL reverse the sort direction and update the visible direction text.
5. THE Plain_View SHALL sort with a stable order, using the mutant id in ascending order as the tie-breaker, regardless of the primary sort direction.
6. IF a Mutant has a status that the Viewer does not recognise, THEN THE Plain_View SHALL show that Mutant's row with the state label "not counted" and SHALL keep the row in the table.
7. THE Plain_View SHALL render no creature graphics and SHALL run no animation or timed visual transition.
8. THE Plain_View SHALL show, for each state, the same count of Mutants as the Verdict_Screen shows for the same Run.
9. THE Plain_View SHALL make every column header reachable with the Tab key and operable with the Enter key and the Space key.
10. WHEN the sort changes, THE Plain_View SHALL set `aria-sort` to "ascending" or "descending" on the sorted column header and SHALL remove `aria-sort` or set it to "none" on all other column headers.
11. IF the Run contains zero Mutants, THEN THE Plain_View SHALL show the table headers with a text message stating that the Run has no Mutants, and SHALL keep the column headers operable.
12. FOR ALL sort columns and directions, THE Plain_View SHALL show the same multiset of rows as the unsorted table (invariant property).
13. FOR ALL columns, sorting by the same column twice in the same direction SHALL produce the same order (idempotence property).

### Requirement 10: Visual system and accessibility

**User Story:** As a user, I want the viewer to follow the bestiary look and be accessible, so that it is readable and consistent.

#### Acceptance Criteria

1. THE Viewer SHALL define the colour tokens `--ink`, `--bone`, `--amber`, `--verdigris`, `--mist` and `--ember` as CSS custom properties on the `:root` element, each with the exact value listed in `bestiary.md`.
2. THE Viewer SHALL use IM Fell English for titles, species names and the headline, and JetBrains Mono with tabular figures enabled for numeric data and code.
3. THE Viewer SHALL bundle both fonts from the `@fontsource` packages through Vite and serve them from its own origin under the `/trick-or-test/` base path, SHALL issue zero network requests to any font CDN or other third-party origin, and SHALL ship the SIL Open Font License text of each font with the built app and show both texts on the Landing_Screen.
4. THE Viewer SHALL render all text with a computed font size of 14 CSS pixels or larger.
5. THE Viewer SHALL pair every state colour with a distinct shape and a visible text label naming the state, so that the state is identifiable without colour.
6. THE Viewer SHALL make every interactive element reachable with the Tab key in DOM order, and SHALL show a focus ring of at least 2 CSS pixels in width with a contrast ratio of at least 3:1 against the adjacent background while the element has focus.
7. WHERE the user's system setting `prefers-reduced-motion: reduce` is active, THE Viewer SHALL run zero animations and SHALL show final states only.
8. WHEN a creature changes to the killed state, THE Viewer SHALL erase its strokes down to bones in 600 ms or less, with at most one animation running at a time.
9. THE Viewer SHALL render no gradient, glow, drop shadow, emoji icon, stock illustration, bitmap monster image or sound.
10. THE Viewer SHALL write all user-facing text in the field-notes voice: sentences of 20 words or fewer, stating facts only, with no exclamation marks.
11. THE Viewer SHALL give each screen a document title that contains the screen name, and exactly one `<h1>` element per screen.
12. IF a font file fails to load, THEN THE Viewer SHALL display text in a fallback font of the same family type (serif for titles, monospace for data and code) and SHALL keep all content and controls usable.

### Requirement 11: Layout and routing

**User Story:** As a user, I want to move between screens and reload the page, so that I can share and revisit a view.

#### Acceptance Criteria

1. THE Viewer SHALL render all screens for a desktop browser with a viewport width of 1024 pixels or more.
2. WHILE the viewport is a Narrow_Screen, THE Viewer SHALL show every screen with the page's scroll width equal to the viewport width (no horizontal page scrolling), and SHALL scroll wide tables horizontally inside their own container.
3. THE Viewer SHALL route screens with the URL hash, so that GitHub Pages serves every route from the single `index.html`.
4. WHEN the user opens a hash route for a Mutant and a Run is loaded, THE Viewer SHALL show the Specimen_Screen for that mutant id.
5. IF the user opens a hash route for a Mutant and the mutant id does not exist in the loaded Run, THEN THE Viewer SHALL show the Landing_Screen with a note that the mutant was not found, and SHALL keep the loaded Run in memory.
6. IF the user opens a hash route that needs a Run, other than `#/demo/before` and `#/demo/after`, and no Run is loaded, THEN THE Viewer SHALL show the Landing_Screen with a note that no run is open.
7. IF the user opens an unknown hash route, THEN THE Viewer SHALL show the Landing_Screen. The routes `#/demo/before` and `#/demo/after` are known routes that need no preloaded Run, and THE Viewer SHALL handle them as defined in Requirement 2.
8. WHEN the user reloads the page on any route other than `#/demo/before` and `#/demo/after`, THE Viewer SHALL discard the loaded Run and apply criteria 4 to 7 to the current hash route. On the demo routes, reloading loads the Demo_Run again as defined in criterion 8 of Requirement 2.
9. THE Viewer SHALL keep the loaded Run in memory only, and SHALL write no user file content to local storage, session storage or cookies.

### Requirement 12: Engineering and delivery

**User Story:** As a maintainer, I want the viewer built to the repository rules, so that it ships on GitHub Pages and stays checked by CI.

#### Acceptance Criteria

1. THE Viewer SHALL be built with Vite, React and TypeScript with the `strict` compiler option enabled, using plain CSS and custom properties, and with no UI kit, CSS framework or chart library in the dependencies of `apps/viewer/package.json`.
2. THE Viewer SHALL import from the engine only the subpath `trick-or-test/report`, and no module of `apps/viewer` SHALL import a `node:` module.
3. THE Viewer build SHALL set the Vite `base` option to `/trick-or-test/`.
4. THE Viewer workspace SHALL pin every dependency in `apps/viewer/package.json` to an exact version (no `^`, `~` or range operators) that was published at least 14 days before the date it is added.
5. WHEN a commit adds a dependency to the Viewer workspace, THE commit body SHALL state the reason for each added dependency.
6. THE Viewer workspace SHALL have its own Vitest project, and WHEN `npm run check` runs, THE Viewer workspace SHALL execute that Vitest project and fail the check if any of its tests fail.
7. THE Viewer SHALL place screens in `apps/viewer/src/screens/` and every module that draws a creature in `apps/viewer/src/bestiary/`.
8. THE Viewer SHALL implement loading, joining, state derivation, sorting and the Creature_Generator as pure functions, in modules that do not import `react` and that are separate from React component modules.
9. THE Viewer SHALL treat every loaded file as untrusted data, and WHEN the Viewer renders an SVG string, THE Viewer SHALL render it only after the Creature_Generator has escaped the characters `&`, `<`, `>`, `"` and `'` in every text value taken from loaded files.
10. THE Viewer test suite SHALL name each test after the acceptance criterion it guards, SHALL put property tests in files named `*.property.test.ts`, and SHALL configure those property tests with the shared fast-check configuration that fixes `seed` and `numRuns` to constant values.
11. THE Viewer SHALL make zero network requests to a backend, an analytics service or any origin other than the origin that serves the Viewer.
12. WHEN a commit adds the `dev`, `build` or `preview` script to the Viewer workspace, THE same commit SHALL add each added script to the commands table of `.kiro/steering/tech.md`.
13. THE Viewer SHALL NOT read, copy or display any number from the design reference in `.trickortest/design/project/` in the Creature_Generator, its configuration, tests or rendered output. Requirement 13 is the one exception: the style sheets under `apps/viewer/src/styles/` take the palette, widths, spacing and sizes that it lists from the reference. No source file or test refers to the path `.trickortest/design`.
14. IF loading or drawing a loaded file fails for any reason, THEN THE Viewer SHALL show an error that states the failure and SHALL keep the application running, so that no untrusted file crashes the Viewer.
15. THE `dev`, `build`, `preview` and `test` scripts of `apps/viewer/package.json` SHALL each run `npm run build -w trick-or-test` before their own command, so that the Viewer works on a fresh checkout without a prior engine build, and the row that criterion 12 adds to the commands table of `.kiro/steering/tech.md` for each of `dev`, `build` and `preview` SHALL state that the command builds the engine first.
16. THE Viewer workspace SHALL take IM Fell English from `@fontsource/im-fell-english` and JetBrains Mono from `@fontsource/jetbrains-mono`, both as dependencies under criteria 4 and 5, and SHALL contain no font file placed by hand (no `apps/viewer/public/fonts/` directory).

### Requirement 14: Demo runs

**User Story:** As a visitor, I want the two demo links to open real runs, so that I see the viewer working on the numbers the engine produced.

#### Acceptance Criteria

1. WHEN the Viewer loads a Demo_Run, THE Loader SHALL fetch `mutation-report.json`, `verdict.json` and `history.jsonl` from `<base>demo/<before|after>/`, which are the names under which the engine writes the Mutation_Report, the Verdict_File and the History_File, and SHALL NOT request `report.json`. Requirement 2 criteria 3 and 4 apply to each of the three files, and the error names the file that failed.
2. THE repository SHALL provide the Demo_Generator as a script at the repository root, run with `npm run demo`, and the commit that adds it SHALL add a row for `npm run demo` to the commands table of `.kiro/steering/tech.md`.
3. THE Demo_Generator SHALL produce every file of both Demo_Runs by running the engine's `measure` command, and SHALL NOT write, copy or edit a report, verdict or history file by any other means, except for the one copy of the "before" `history.jsonl` described in criterion 7.
4. THE Demo_Generator SHALL build the engine first, SHALL remove the files of an earlier run from `apps/viewer/public/demo/before/` and `apps/viewer/public/demo/after/` before it starts, so that running it twice gives the same files, and SHALL leave `reports/` and `examples/pricing/` unchanged.
5. THE Demo_Generator SHALL generate the "before" Demo_Run by running `measure` on `examples/pricing` as it is, with the `cart-pricing` spec and `apps/viewer/public/demo/before` as the output directory.
6. THE Demo_Generator SHALL generate the "after" Demo_Run by running `measure` on a throwaway copy of `examples/pricing` under `.trickortest/` (git-ignored), with the `cart-pricing` spec and `apps/viewer/public/demo/after` as the output directory. THE copy SHALL contain the Guard_Test and SHALL NOT contain `node_modules`, earlier reports or working files of an earlier run, and THE Demo_Generator SHALL remove the copy when it finishes.
7. BEFORE it runs `measure` for the "after" Demo_Run, THE Demo_Generator SHALL copy `apps/viewer/public/demo/before/history.jsonl` to the "after" output directory, so that the engine appends the "after" record as the second line and the "after" `history.jsonl` holds exactly two records, the first byte-identical to the "before" record.
8. THE Guard_Test SHALL be one committed test file outside `examples/pricing/test/` (so the example's own test suite and its files do not change), SHALL be an example test (`*.test.ts`) whose names start with the criterion id `7.4`, SHALL assert that a discount never makes a field of the Breakdown negative, and SHALL kill the Spec_Mutant `oath-7.4-negative-discount-allowed` when run in the copy. THE copy SHALL run the Guard_Test together with the example's own tests.
9. THE "before" Verdict_File SHALL hold `oath-7.4-negative-discount-allowed` as a surviving Spec_Mutant, and THE "after" Verdict_File SHALL hold it as killed, so that the "after" History_File record lists it in `newlyKilledIds` and the Hunt_Screen of the "after" Demo_Run shows two runs with that Mutant newly killed in the second.
10. THE generated files under `apps/viewer/public/demo/` SHALL be committed, SHALL never be edited by hand, and SHALL contain no absolute path (no `/home/`, `/Users/`, drive letter, `/tmp/` or repository root path, and no `.trickortest` path).
11. THE Viewer test suite SHALL NOT depend on the presence of `apps/viewer/public/demo/` (Requirement 2 criterion 6), except for the one structural test of criteria 1, 9 and 10 that reads the committed demo files and asserts ids, file names and the absence of absolute paths, and no test SHALL assert a count taken from them.
